kubectl apply 一个 deployment.yaml 到服务正常运行的中间过程

K8s 核心
考点：端到端控制面数据流。建议按「客户端 → API → 控制器 → 调度 → kubelet → CRI」五段式回答，每一环都要能说出组件名和动作。
kubectl 客户端→ apiserver 认证/准入→ etcd 持久化→ Deployment/ReplicaSet 控制器→ Scheduler 调度绑定→ kubelet + CRI/CNI/CSI→ 容器运行、状态回报

① 客户端阶段

  • kubectl 读取并校验 YAML，把 Deployment 与当前集群里的版本做 three-way merge（last-applied-configuration 注解 / server-side apply 时用 managedFields），生成 Patch 或完整对象。
  • 通过 HTTP(S) 发送请求，请求头携带客户端证书 / Bearer Token。

② apiserver 阶段（写路径）

  • 认证 Authentication：证书 / Token / OIDC 确认用户身份。
  • 鉴权 Authorization：RBAC / Node / Webhook 判断是否有权限。
  • 变更准入 MutatingAdmission：注入默认值（如 strategy 滚动参数）、sidecar 注入 webhook 等。
  • Schema 校验：OpenAPI 校验字段合法性。
  • 验证准入 ValidatingAdmission：策略校验（如镜像白名单）。
  • 通过后写入 etcd（走 raft 共识 + WAL 持久化），并在 watch 环形缓存中广播事件，此时 Pod 还一个都没创建。

③ 控制器阶段（controller-manager）

  • Deployment Controller watch 到新 Deployment，按 rollout 策略创建新的 ReplicaSet。
  • ReplicaSet Controller 根据 replicas 创建 N 个 Pod 对象（spec.nodeName 为空，处于 Pending）。

④ 调度阶段（scheduler）

  • 调度器从调度队列取出 nodeName 为空的 Pod：先 过滤 Filter（资源、亲和性、污点容忍、端口、PV 绑定），再 打分 Score（资源均衡、镜像本地性、spread），选出最优节点。
  • 先在内存中 assume（乐观占位），再异步调用 apiserver 执行 Binding 写回 nodeName。

⑤ 节点阶段（kubelet）

  • kubelet watch 到被调度到本节点的 Pod，先做 Admit（资源校验），再走 CRI 拉镜像并创建容器（containerd → containerd-shim → runc）。
  • CNI 分配 Pod IP 并配置网络；CSI 挂载卷（若有）。
  • 容器启动、探针就绪后 Endpoint/EndpointSlice 更新，Service 流量切入，服务进入正常运行状态；kubelet 持续上报状态到 apiserver。
追问预案：为什么此时 Deployment 还没"Running"——因为 K8s 是声明式 API + 控制循环（level-triggered），各组件通过 watch 事件趋向终态，而不是命令式调用链。

Informer 机制，apiserver watch cache 的实现

K8s 核心
考点：客户端 Informer 是「List-Watch + 本地缓存 + 事件分发」，服务端 watchCache 是「etcd watcher 的 fan-out 缓存」。两端要分开讲。

客户端 Informer（client-go）

  • Reflector：执行 ListAndWatch——先 LIST 全量对象拿到 resourceVersion，再从该版本开始 WATCH 增量事件。
  • DeltaFIFO：把事件包装成 Delta（Added/Updated/Deleted/Sync）进入队列，起到解耦与去重作用。
  • Indexer / 本地 Store：processLoop 消费 Delta，把对象写入带索引的本地缓存（如按 namespace 查询），后续 Get/List 都打本地缓存，不打 apiserver。
  • EventHandler：回调 OnAdd/OnUpdate/OnDelete，通常把 key 投递到 workqueue，由 controller 的 worker 消费，实现失败重试与限速。
  • 断线后按 resourceVersion 重连；若版本过期（410 Gone）则退化为重新 LIST。

服务端 watchCache（apiserver 内部）

  • apiserver 对每种资源维护一个 watchCache：只向 etcd 建立少量长连接 watcher，事件写入内部 环形缓存（eventCache）。
  • 成千上万个客户端 WATCH 请求由 apiserver fan-out：watcher 注册到 watchCache，从缓存中按 resourceVersion 回放/推送事件，而不是每个客户端都打一次 etcd。
  • LIST 请求也可由 QuorumRead / 缓存读处理（consistency 配置），降低 etcd 压力。
  • watch bookmark（CHECKPOINT）：定期发送 Bookmark 事件推进客户端 resourceVersion，减少重连时的全量 LIST。
一句话背诵：Informer = Reflector(List+Watch) + DeltaFIFO + Indexer 本地缓存 + EventHandler/Workqueue；watchCache = apiserver 对 etcd watcher 做的环形缓存 + fan-out，使海量 watch 不打爆 etcd。

Containerd 怎么保证自身进程退出时容器不退出

容器运行时
核心答案：容器 1 号进程的父进程不是 containerd，而是 containerd-shim；shim 与 containerd 解耦，containerd 挂了不影响容器生命周期。
  • 架构分层：containerd（守护进程）→ containerd-shim（每容器一个进程，v2 为 runc-shim / shim API）→ runc（创建后退出）→ 容器 init 进程。runc 创建完容器就退出，容器 init 进程被 reparent 到 shim。
  • 职责隔离：shim 负责容器的 stdio 管道、信号转发、exit 状态收集和 cgroup 管理；它独立于 containerd 的生命周期。
  • 故障场景：containerd 崩溃或升级重启时，shim 与容器继续运行；containerd 重启后通过 shim 的 socket 重新恢复对容器的管理（reload）。
  • 对比：早期 Docker（containerd v1 集成前 / dockerd 一体架构）挂掉会影响容器，所以才演进出 shim 解耦架构；K8s 场景下 kubelet → CRI → containerd，同理 kubelet 重启也不杀容器。
  • 补充：容器内进程退出后，若 containerd 不在，shim 仍能保留僵尸态并上报退出码（containerd 重启后消费）；systemd 场景下 cgroup driver 委托 systemd，进一步保证状态一致。
追问预案：kill 掉 shim 会怎样——容器 init 进程 reparent 到上一级（通常 containerd 或 systemd），stdio 断开可能导致容器异常，所以 shim 才是关键守护层。

Go：GMP 模型、channel 的用法、slice 在函数调用时的表现

Go 语言
考点：三小题连问，每题都要"机制 + 关键数据结构 + 边界 case"。

GMP 调度模型

  • G（goroutine，含栈和状态）、M（内核线程）、P（调度上下文，数量 = GOMAXPROCS，持有本地运行队列）。
  • M 必须绑定一个 P 才能执行 G；G 优先在 P 的本地队列运行，满了溢出到全局队列。
  • work stealing：本地队列空了，先偷其他 P 的一半 G，再查全局队列（有兜底配额），再查netpoller（网络就绪的 G）。
  • 阻塞处理：G 阻塞在 channel/syscall 时 M 可能阻塞，P 会解绑交给其他 M（handoff）；系统调用由 sysmon 监控超时后抢占 P。
  • 抢占：Go 1.14+ 基于信号（SIGURG）的异步抢占，解决长时间计算循环饿死问题；G 超过约 10ms 被抢占。

channel 的用法与底层

  • 用法：无缓冲（同步交接）、有缓冲（解耦/生产消费）、select 多路复用、close 广播退出（ctx.Done 原理）、用 channel 做信号量/超时模式。
  • 底层 hchan：mutex + 环形缓冲区（buf）+ sendq/recvq 等待队列（sudog）+ closed 标记。
  • 边界 case（高频追问）：向 nil channel 收发 → 永久阻塞；向 已 close 的 channel 发送 → panic；从已 close 且为空的 channel 接收 → 立即返回零值（第二个返回值 false）；close nil channel → panic；重复 close → panic。关闭应由发送方负责。

slice 在函数调用时的表现

  • slice 本质是 SliceHeader{Data 指针, Len, Cap}，按值传递（三个字段拷贝），但底层数组共享。
  • 函数内原地修改元素 → 调用方可见（共享底层数组）。
  • 函数内 append 未超 cap → 写同一数组，调用方"可能"看到长度内的新值（len 变化不可见）。
  • 函数内 append 触发扩容 → 申请新数组，修改对新数组的操作，调用方完全不可见。
  • 最佳实践：需要函数内可靠扩容时传指针或返回新 slice；预分配 cap 避免多次扩容。

超大规模集群 apiserver 及 etcd 的性能瓶颈在哪里，怎么优化

大规模/性能
答题框架：先分「写路径（etcd）」「读路径（LIST/缓存）」「watch 路径（fan-out 内存）」三条线找瓶颈，再逐一给优化手段。

主要瓶颈

  • etcd 写入：raft 复制 + WAL fsync + btree 索引，单写点，QPS 上限约 1w 级；请求越大越慢。
  • 大 LIST：全量列举大对象（如 Pod/CRD）非常昂贵，易打爆 apiserver 内存与 etcd。
  • watch fan-out：海量 watcher + 事件广播消耗 apiserver 内存与 CPU。
  • etcd compaction/碎片：历史版本堆积导致 db 膨胀、defrag 期间不可写。
  • apiserver 队头阻塞：贵请求（大 LIST）占满 goroutine/内存，影响所有请求。

优化手段

  • etcd 层：定期 compact + defrag；拆分事件存储（默认可把 events 拆到独立 etcd）；SSD/低延迟盘、独立部署；监控 db 大小与 fsync p99。
  • apiserver 层：横向多副本 + LB；开启 APF（API Priority and Fairness）隔离贵请求；protobuf 序列化；watch bookmark 减少重连 LIST。
  • 客户端层：Informer 本地缓存 + 分页 LIST + WatchList（流式 list）替代全量 LIST；避免在集群里跑"扫全库"的监控任务。
  • 架构层：CRD 大对象瘦身 / 移到外部存储；SSA（Server-Side Apply）替代大注解；联邦/多集群拆分爆炸半径；大规模场景引入代理缓存层（如 virtual kubelet / 分级 apiserver）。
加分项：给出数量级感知——etcd 推荐 < 8GB db、单集群官方到 5k 节点（经优化可到 1w+），Node/pod 对象百万级时 LIST 是首要杀手。

原生调度器的实现、大规模集群下的性能瓶颈与优化、AI 场景下的局限性

调度器
考点：调度周期流程 → 吞吐瓶颈 → Scheduling Framework → AI/gang 调度缺失。

实现（一个调度周期）

  • 调度队列（active/backoff/unschedulable 三队列，优先级 + backoff）取出 Pod。
  • 构建 SchedulerCache 快照 Snapshot（保证同一周期内视图一致）。
  • Filter 过滤（预选）：资源、亲和/反亲和、污点、拓扑域、卷绑定等插件链。
  • Score 打分（优选）：LeastAllocated、均衡度、镜像本地性、NodeAffinity 等，加权求和。
  • Assume + 异步 Bind：先在缓存假设调度成功，再异步调用 apiserver 写 Binding，提高吞吐。
  • 通过 Scheduling Framework 的扩展点（QueueSort/PreFilter/Filter/PostFilter/Reserve/Permit/PreBind/Bind）注入自定义逻辑。

大规模瓶颈与优化

  • 瓶颈：单调度器串行周期、节点数千时 Filter/Score 计算量大、Pod/Node informer 缓存内存、大量失败 Pod 的重试风暴。
  • 优化：调度吞吐参数（提高并发 goroutine、percentageOfNodesToScore 截断——打分只采样部分节点）；Snapshot 增量更新；Reserve/Permit 阶段减少绑定失败回滚；多调度器（多 scheduler profile / shard）分域；失败 Pod 指数退避。

AI 场景局限性

  • 原生是独立调度（逐 Pod），缺少 gang scheduling：分布式训练全组 Pod 必须同时就位，否则部分 Pod 空占 GPU 死锁。
  • 缺少拓扑约束：GPU 机型、NVLink/RDMA 网络域需要"整组放同一拓扑域"，原生 PodAffinity 表达力与性能不足。
  • 缺少队列与配额体系：作业排队、抢占、公平共享需要 Kueue/Volcano 等上层系统。
  • BinPack 与算力碎片：GPU 亲和默认策略易产生碎片；弹性训练（弹性 rank、checkpoint 恢复）与调度联动缺失。
  • 解决生态：Volcano（gang/predicates 扩展）、Kueue（队列+配额+抢占）、K8s Device Plugin + DRA（动态资源分配）、Topology Aware Scheduling。

apiserver 在社区的演进方向

社区动态
主线：可扩展性（大规模）、可扩展点（扩展性）、声明式简化、安全与策略内建。
  • 可扩展性：WatchList（streaming list）——用 watch 流式建立缓存替代大 LIST，显著降低 apiserver/etcd 压力；一致性读与缓存读的平衡；storage version migration 让 etcd 统一存储版本。
  • 声明式简化：Server-Side Apply（GA）+ managedFields，取代客户端 last-applied 合并。
  • 策略内建：ValidatingAdmissionPolicy（CEL 表达式）替代部分 admission webhook，降低运维与延迟成本。
  • 扩展机制：CRD 持续增强（CEL validation rules、defaulting、beta 级别演进）、Aggregated API Server（AA）做多 apiserver 聚合。
  • 资源管理：DRA（Dynamic Resource Allocation）——通用化的 GPU/ FPGA 等资源分配，取代专用 Device Plugin 的调度盲区。
  • 稳定性：APF 优先级与公平性继续打磨、可观测性（APIServer tracing/metrics）、安全（匿名权限收紧、ServiceAccount token 边界改进）。
提示：面试时报出 WatchList、SSA、CEL 准入、DRA 四个关键词即可体现对社区的跟踪。

联邦集群与常规集群的差异和优化点

多集群
核心：常规集群管"单集群内的 Pod"，联邦/多集群方案管"集群的集群"——分发、差异化、全局视图、故障转移。

差异

  • 抽象层级：联邦（KubeFed / Karmada / Clusternet / OCM）引入模板（ResourceTemplate）+ 传播策略（Placement）+ 差异化（Overrides/Replicas 分配）三层概念；常规集群只有单层对象。
  • 作用域：跨 region/云/机房统一管理，统一 API 入口；常规集群爆炸半径就是一个集群。
  • 调度对象：联邦调度的是"集群"这个单元（选哪个集群、每个集群几副本），集群内仍由各自 scheduler 调度。
  • 故障转移：联邦可检测集群失联后把工作负载迁移到健康集群；单集群只能做 Pod/Node 级漂移。

优化点 / 挑战

  • 最终一致：控制面到多集群的分发是异步的，需处理版本冲突、回传聚合状态（AggregateStatus）。
  • 网络：跨集群服务发现（MultiCluster DNS / ServiceExport）、东西向流量（Cilium ClusterMesh、istio 多集群）。
  • 成本：按就近/成本策略分配副本（动态 weight）、避免跨区流量费用。
  • 爆炸半径与治理：配置灰度分发（按集群分批）、策略统一下发（OPA/Kyverno）、差异化的资源配额。

K8s 怎么做集群升级

运维
主线：版本偏斜政策 + 控制面先行 + 节点滚动 + 数据备份。
  • 版本偏斜政策（先背）：kube-apiserver 各组件版本必须一致；kubelet 最多落后 apiserver 两个 minor 版本；kubelet 之间不能跨两个 minor；升级必须逐 minor 递进（如 1.28→1.29→1.30，不能跳级）。
  • 升级顺序：备份 etcd 快照与配置 → 升级控制面（kubeadm upgrade / 云厂商托管升级）：先 etcd，再 kube-apiserver，再 controller-manager/scheduler → 升级 kube-proxy → 逐个升级节点上的 kubelet/kubelet 依赖。
  • 节点滚动：cordon + drain（遵守 PDB 控制中断）→ 升级 kubelet 与容器运行时 → uncordon → 观察后下一批；可先升级 1-2 台金丝雀节点验证。
  • 兼容性检查：kubeadm upgrade plan、deprecated API 检查（如每个版本移除的 API，1.32 移除 flowcontrol v1beta 等）、CNI/CSI/负载均衡组件版本兼容矩阵。
  • 托管集群：EKS/GKE/ACK 由厂商滚动升级控制面，用户负责节点池与插件；注意 apiserver HA 逐实例升级期间的短暂抖动，客户端要带重试。
  • 风险控制：升级窗口、回滚预案（多数场景控制面不可回滚，只能靠备份重建）、升级后验证（node ready、pod 重调度、webhook 可用性）。

智能调度要怎么做，会遇到的主要问题是什么

AI + 调度
答题框架：目标（更优的放置决策）→ 输入（数据）→ 方法（预测/学习/优化）→ 四大问题（数据、预测漂移、反馈震荡、可解释性）。

怎么做

  • 负载预测：基于历史时序（真实使用率而非 request）预测未来负载，用于资源超卖、节点整合（binpack 省资源）与潮汐混部。
  • smarter 过滤/打分：把成本、公平性、干扰（interference）、SLO 延迟目标纳入 Score 插件；多目标优化（如装箱率 vs 均衡度）。
  • 强化学习/求解器：用 RL 学放置策略，或用 OR-Tools 等求解器做全局最优重排（重调度 rebalance）。
  • 闭环：预测 → 调度 → 实测反馈 → 模型迭代；配合 Descheduler 做纠偏。

主要问题

  • 数据问题：监控数据稀疏/噪声大，request 与实际用量脱节，冷启动无历史。
  • 预测漂移：业务突变（大促、训练作业突发）让模型失效；预测错误比保守策略危害更大。
  • 反馈震荡（最常被追问）：智能决策改变系统状态 → 状态变化使模型假设失效 → 决策反复翻转（调度抖动、Pod 迁移风暴），需要滞后带/最小迁移间隔/全局协调。
  • 干扰建模难：混部下 CPU 缓存/IO 互相干扰，难以量化 LRE（降低的运行效率）。
  • 可解释性与安全兜底：AI 决策出错影响生产，必须有回滚和兜底策略；算法决策要能被 SRE 审计。

用什么 code plan？演示怎么用 Codex 完成某个场景题的架构设计和优化

AI 编码
考点：是否真的把 AI 编码工具（Codex / Claude Code / Copilot Workspace 等）融入工作流，有没有"先规划后编码"的方法论。

Code Plan 工作法

  • Plan 模式先行：让 Agent 处于只读规划模式，先产出方案（架构图、文件改动清单、里程碑），人工评审后再进入执行模式逐条实施。
  • 任务拆分：把场景题拆成里程碑（骨架 → 核心链路 → 测试 → 优化），每步给出验收标准，控制 Agent 每次改动的爆炸半径。
  • 上下文供给：给 Agent 提供 AGENTS.md / 项目规范、关键接口定义、性能基线数据；让它先读代码再提案。

演示示例：场景题"设计一个支持 10k 节点的指标采集系统并优化"

  • 第一步（Plan）：向 Codex 描述需求与约束（节点数、采样周期、存储成本），要求输出：候选架构（push/pull、分层聚合、存储选型）对比表 + 推荐方案 + 风险清单。
  • 第二步（评审）：人工确认选型（如 pull 模型 + 边缘 agent 预聚合 + TSDB 分层存储），让 Codex 把方案写成 design doc，并列出每一步的 TODO。
  • 第三步（实现）：逐 TODO 生成代码骨架与单元测试，Codex 边写边跑测试；每个里程碑提交一次，方便回滚。
  • 第四步（优化）：让 Codex 写压测脚本 → 跑基准 → 定位瓶颈（序列化/批量写入/索引）→ 提出优化 patch 并用数据对比前后差异。
加分点：强调"AI 出方案、人做决策、验收标准前置、测试驱动闭环"，以及用 repo 级上下文文件（AGENTS.md / CLAUDE.md）固化规范。

是否了解 AI Ops？怎么看待？当前的主要问题是什么？

AIOps
答题姿势：先给定义与分层落地场景（体现了解），再给自己的判断（体现"怎么看待"），最后讲问题与边界（体现深度）。

是什么

  • 用 AI/ML 增强运维：异常检测（时序基线替代静态阈值）、告警降噪与聚合（事件压缩 + 关联分析）、根因定位（RCA）（调用链/拓扑 + 图分析）、容量预测、变更风险检测、ChatOps 式的 LLM 运维助手（查日志、生成 runbook、辅助排障）。
  • LLM 时代的新形态：自然语言查询集群状态、故障时自动拉取日志/metrics/traces 做初步诊断并生成修复建议，与 DevOps 平台集成（如 k8sgpt 类工具）。

怎么看待

  • 价值在于降人力和 MTTR：告警风暴处理、重复性排障最适合 AI；确定性规则能解决的不必上模型。
  • 合适的落地路径是"AI 建议 + 人决策"逐步过渡到"低风险操作自动闭环"，而不是一步到位全自动。

当前主要问题

  • 数据质量：多源数据（log/metric/trace/event）口径不一、缺失、语义没有统一，模型输入先天不良。
  • 幻觉与不可解释：LLM 生成的诊断/修复建议可能看起来合理但错误，生产事故场景无法容忍，需要工具校验与溯源。
  • 闭环风险：自动执行变更/扩缩容一旦误判会放大故障；需要权限隔离、灰度、熔断与一键回滚。
  • 泛化性差：每个系统的故障模式与拓扑不同，模型难以跨系统复用，标注成本高。
  • 成本与时效：LLM 推理延迟与费用，难以满足秒级告警响应，需分级（小模型过滤 + 大模型深分析）。
